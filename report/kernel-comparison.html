What BORE actually buys, measured three ways

A linux-omarchy-bore 7.2.2-5 kernel — built on Apple Silicon with a self-compiled Arch GCC 16.2.1 cross-toolchain — measured against Arch's own linux 7.2.2 binary, and against itself with the BORE scheduler switched off at runtime. Same machine, same upstream version, same afternoon.

A deliberate trade, and it lands the right way up

With upstream version and hardware held constant, the custom kernel switches tasks 23 % faster than Arch's own build and runs hackbench 14 % faster — the two measurements closest to how a desktop actually feels. It pays for that with 21 % less throughput under sustained mutex contention, a workload no desktop performs. Isolating the scheduler shows BORE is what buys the responsiveness, not what costs it.

Where the scheduler shows up — and where it does not

First pass — against Arch 7.1.11

The original comparison, before the version and scheduler variables were separated. Kept because the hardware and boot findings still stand; its contention conclusion is superseded by the decomposition below.

Boot is 3.3 s faster overall better

Userspace startup fell from 9.72 s to 6.06 s (−38 %). Kernel init was unchanged at ~3.3 s.

Initrd 384 ms slower flagged, not real

The only metric to trip the automatic 10 % regression threshold (3263 ms → 3647 ms). Both boots unlock LUKS from the TPM, and that handshake varies by a few hundred milliseconds run to run. Two samples cannot separate a real change from that noise — and the same boot gained 3.7 s in userspace, so total time to desktop still improved.

Loaded latency crossed a threshold boundary artifact

cyclictest_loaded flipped PASS → WARN purely because 981 µs sits just under the 1 ms line and 1036 µs sits just over it. A 55 µs difference is not perceptible; the status change is the grading boundary, not the kernel.

Display detection differed environmental

The stock run saw no connected output and one compositor monitor; the BORE run saw HDMI-A-1 at 3840×2160 plus a VNC output. Most likely the physical display was asleep during the stock run rather than a driver difference — both kernels bound i915 cleanly with zero DRM errors. Worth re-checking with the monitor confirmed awake.

Suspend and resume clean on both newly verified

Two S3 deep cycles per kernel via rtcwake, with every NIC, DRM card and sound card confirmed present afterwards and no PM errors in the log. Worth noting this machine had never suspended before today — zero prior suspend events in its journal — so this was an untested path on both kernels, not just the new one.

BORE scheduler confirmed active expected

kernel.sched_bore=1 on the new kernel and absent on stock — the one status change that is supposed to happen. hackbench also improved 9 % (3.70 s → 3.38 s), inside tolerance but pointing the right way.

What was not run

Stated plainly, because their absence bounds what this report can claim:

Sustained stressThe 20-minute stress-ng CPU/VM/IO/matrix soak with thermal tracking was not part of this comparison — only the 5-minute load used to pressure the latency test. A thermal or long-run stability difference would not have surfaced here.
Repeat samplingContention was sampled five times on the custom kernel (~1 % spread) and three times per BORE state, but once per configuration for the rest. Enough to trust differences of this size; not enough to resolve a few percent.
Config attributionStill open. A full config diff found only one scheduler-relevant difference from Arch (RCU_NOCB_CPU_DEFAULT_ALL), and testing it ruled it out as the cause — see below. What remains untested is the 59 non-BORE patches in the Omarchy kernel and the self-built cross-compiler.
Real applicationsEverything here is a microbenchmark. None of it measures frame pacing, input latency or application launch time, which is what "feels smooth" actually means.

Isolating the scheduler — three configurations

The first comparison confounded three variables: upstream version, kernel config, and the BORE scheduler. Two of them were removable without building anything. Arch ships linux 7.2.2 as a binary, matching the custom kernel's upstream version exactly; and BORE has a runtime switch, so the same binary can be measured with the scheduler on and off. What the decomposition shows

BORE is what makes task switching fast −32 %

On the identical binary, switching BORE on takes context-switch cost from 7.73 µs to 5.23 µs and hackbench from 4.76 s to 3.38 s. That is not a marginal tuning effect — it is the largest single change measured here, and it lands on the metrics closest to how a desktop feels: every window focus, input event and compositor frame is task switches.

The config, not BORE, causes most of the contention loss corrects earlier reading

The first comparison blamed BORE for a 21 % contention deficit. Splitting it shows the Omarchy config and cross-compiler account for about 15 % (29,237 → 24,945 with BORE off) and BORE for roughly 8 % on top. BORE was carrying blame for something largely not its doing.

BORE more than repays the config's penalty net win

With BORE off, the custom kernel is worse than Arch's at context switching — 7.73 µs against 6.75 µs. Switching BORE on does not merely recover that gap, it ends up 23 % ahead of stock. The same pattern holds for hackbench: 4.76 s becomes 3.38 s against stock's 3.95 s.

RCU offloading is a latency win, not the throughput cost hypothesis disproved

A full config diff turned up exactly one scheduler-relevant difference from Arch: Omarchy sets CONFIG_RCU_NOCB_CPU_DEFAULT_ALL=y, moving RCU callback processing off every CPU into dedicated kthreads. The obvious theory was that the extra kthread wakeups cost throughput.

Testing it by booting with rcu_nocbs=0 — offloading only CPU 0 instead of all four — showed the opposite. Contention throughput barely moved (23,038 → 22,748, about 1 %), so offloading is not the cost. But context-switch latency got 69 % worse, 5.23 µs → 8.85 µs, because RCU softirq work then runs on the CPUs doing the actual work and interrupts it. Omarchy's choice is well founded, and the theory was backwards.

Upstream version explains none of it ruled out

Arch's 7.2.2 scored 29,237 against 7.1.11's 28,848 on the contention benchmark — marginally better, not worse. The 7.1 → 7.2 caveat carried in the earlier version of this report can be retired.

The remaining ~15 % is still unexplained open

Upstream version is ruled out, BORE accounts for about 8 %, and the one config difference turned out to be a latency benefit rather than a throughput cost. That leaves the Omarchy kernel's 59 other patches and the self-built cross-compiler, neither of which has been isolated. Two theories have already been tested and discarded here; a third would be a guess, so it is left open.

Timer latency is not where BORE shows up unchanged

cyclictest is flat across all three configurations (963–968 µs idle, 971–1036 µs loaded). It measures timer wakeups for a real-time-priority thread, which BORE does not govern. The scheduler's effect appears in ordinary task switching instead — which is why both measurements belong in the suite.

How to read this

One run per kernel, one machine, one sitting. Everything inside ±10 % is reported as “~same” rather than as an improvement or a regression, because two samples cannot resolve that range. The desktop was idle but live during both runs — a compositor and a full session, not a bare console — so these numbers reflect a real working machine rather than a laboratory floor.
